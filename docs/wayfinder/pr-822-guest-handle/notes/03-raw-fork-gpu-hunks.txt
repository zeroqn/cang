    feat(gpu): re-add the render-server fd entry point and fence retirement on ABI 2
    
    ABI 2 replaced the v1 `krun_set_gpu_options3` with an object-model GPU device that
    only takes virgl renderer flags and a display backend, so cang's `--gpu=drm`
    venus render-server path had no way to hand virglrenderer the socketpair. Re-add
    it on the device:
    
    - `GpuDevice::set_render_server_fd(fd)` validates the fd, takes ownership of it,
      and stores it so `attach` can pass it to `Gpu::new`;
      `VirtioGpu::create_rutabaga` then sets it as rutabaga's server descriptor,
      which is what reaches virglrenderer's render-server callback.
    - Thread the descriptor as `Option<OwnedFd>` through Gpu -> Worker -> VirtioGpu,
      so libkrun owns it and closes it on every error path.
    
    Bring the virtio-gpu device fixes with it, because they were what made that path
    work at all:
    
    - The gpu worker polled only the control queue eventfd, so
      `vrend_renderer_check_fences` was never called and the guest hung on
      `DRM_IOCTL_VIRTGPU_WAIT` for fenced execbufs. It now polls the control event
      and the virgl fence-retirement descriptor together, and calls `event_poll` on
      timeout while a fence is pending (video-decode fences land in vrend's
      fence_list, not fence_wait_list, so the eventfd is not signalled for them).
    - The fence descriptor is kept alive for the worker's lifetime; mapping it to a
      raw fd dropped and closed it on the first loop iteration.
    - The fence handler recovers poisoned queue/fence-state locks instead of
      panicking: it runs inside virglrenderer's C callbacks, which abort the process
      on unwind.
    - An idle VM blocks indefinitely instead of waking every 10ms: the short poll
      timeout is only used while a fenced descriptor is outstanding.
    
    Regenerated bindings follow in their own commit.
