# Cache symlinks shipped — FUSE_CACHE_SYMLINKS (fork v2.0.0-cang.15)

**Verdict: the largest request-removing lever left, and it is one bit.** `CACHE_SYMLINKS`
(`1 << 23`) has been defined in the fork's `fuse.rs` since the crosvm import and was never OR'd
into the init reply, so the guest could not keep a symlink's target: every resolution of the same
symlink cost a `READLINK` round trip. Advertising it - behind a per-device switch, off by default
like the other request-removing switches - removed **98-99% of the `READLINK`s** and **28-65% of all
requests** across the five workloads profiled here, with `READ`, `LOOKUP` and `GETXATTR` unchanged
in every pair.

## 0. Where the requests were

All numbers are the share's own opcode histogram (`CANG_FS_STATS=1`), defaults as shipped
(zero-message open, no-flush, 250 ms negative entry), same workload on both sides of each pair, and
the workload did identical work (`EXEC_COUNT=600`, `NIX_READ=1500`, `WS_READ=2000`, `WROTE=200`,
`APPENDS=200`, final journal size 819,200 B). Every path here is on the **one** virtio-fs connection:
`/`, `/workspace`, `/nix`, `/home/dev/.codex` are grafts inside a single root export, announced to
the guest as `FUSE_ATTR_SUBMOUNT` sub-volumes, so `INIT` is 1 in every arm and a lever is
connection-wide, not per mount.

| workload | requests | `READLINK` | share |
|---|---|---|---|
| 600 execs of `/bin/true` | 11,522 | 5,242 | 45.5% |
| 1500 `/nix/store/*/bin/*` reads | 29,350 | 18,941 | 64.5% |
| 2000 `/workspace/data/*` reads | 38,230 | 24,442 | 63.9% |
| 200 compiler-cache write+rename+read rounds | 22,854 | 7,666 | 33.5% |
| 200 append+stat rounds in `/home/dev/.pi` | 11,861 | 5,278 | 44.5% |

## 1. The lever, measured

| workload | before | after | `READLINK` | `LOOKUP` | `READ` |
|---|---|---|---|---|---|
| exec loop | 11,522 | 7,737 (-33%) | 5,242 -> 95 | 3,440 -> 4,774 | 1,468 -> 1,477 |
| `/nix` reads | 29,350 | 12,798 (-56%) | 18,941 -> 530 | 5,080 -> 6,918 | 2,519 -> 2,526 |
| `/workspace` reads | 38,230 | 13,362 (-65%) | 24,442 -> 93 | 7,509 -> 6,963 | 3,480 -> 3,492 |
| cache write+rename+read | 22,854 | 15,768 (-31%) | 7,666 -> 95 | 4,904 -> 5,395 | 2,073 -> 2,086 |
| `.pi` appends | 11,861 | 8,565 (-28%) | 5,278 -> 96 | 3,308 -> 5,172 | 1,479 -> 1,497 |

`LOOKUP` moves *up* in three arms: with the link target cached the kernel walks the target's
components itself, so components that used to ride a `READLINK` reply now arrive as their own
lookups. It is a good trade - one request either way, and the `READLINK` carried a payload - and it
is why `LOOKUP` is now ~45-55% of what is left, i.e. the `entry_timeout` class.

## 2. Where it came from, and where it is wired

Fork commit `eff52c5d` on `zeroqn/libkrun` `cang`, tag **`v2.0.0-cang.15`**:
`Config.cache_symlinks` (default `false`), honoured in `linux/passthrough.rs::init()` only when the
client offers `CACHE_SYMLINKS`; `FsDevice::set_cache_symlinks` from Rust and
`krun_fs_device_set_cache_symlinks` from the C API, with `bindings/…/ffier-krun.json` and
`include/libkrun.h` regenerated by `make gen-libkrun-bindings` (ffier 0.2.0rc1) and `CANG.md`
updated. cang turns it on by default (`cang_libkrun::CANG_FS_CACHE_SYMLINKS`), overridable with
`CANG_FS_CACHE_SYMLINKS=0|1` and `--fs=cache-symlinks:on|off`; the launcher records
`krun_fs_device_set_cache_symlinks`, and 647 cang lib tests plus a fork unit test
(`cache_symlinks_is_advertised_only_when_configured_and_offered`) cover it.

The unit test is the one worth keeping: the flag is claimed **only** when the caller asked for it
*and* the client offered it, because claiming a capability the client cannot use would silently
change nothing while looking shipped.

## 3. Cost

A symlink the **host** retargets stays stale in the guest for the entry's validity -
`entry_timeout`, 5 s by default - the same window zero-message open already exposes file contents
to. A target that never changes (every `/nix/store` entry) costs nothing, and a workspace that needs
strict resolution runs `--fs=cache-symlinks:off`.

## 4. What this says about the remaining request classes

Instrumenting the server's `GETXATTR` names and `LOOKUP` names (a throwaway fork build, not
shipped) over the same five workloads settled two questions:

- **`GETXATTR` is `security.capability`, and nothing else** - one name, `distinct=1` in every arm
  (3,714 in the cache arm, 2,113 in the workspace arm, 715 in the append arm, 40 in the exec arm).
  It is the kernel's exec-time file-capability probe: one request per process start. No FUSE-level
  cache can remove it (the protocol has no xattr cache and the kernel re-probes on every exec); the
  only lever is `Config.xattr = false`, which makes the server answer `-ENOSYS`, the client stop
  asking, and **file capabilities stop being honoured in the guest** - a price to charge only on a
  share where nothing carries capabilities.
- **The remaining `LOOKUP`s are loader and runtime probes**, not stale positive entries:
  `glibc-hwcaps` (461 of 7,355 in the workspace arm), and repeated misses for the OCI runtimes
  podman probes at boot (`runsc`, `crun-vm`, `runj`, `youki`, 144 each - a count above the 250 ms
  negative-entry lifetime because the probes are spread across boot). Positive entries are already
  cached at 5 s; the lever there is a longer negative lifetime on an immutable share, which is
  what a read-only `/nix` export would make safe.

## 5. `entry_timeout` is measured and does not pay (2026-11-03)

The setters exist in the fork as commit `3c2eb13b` (`FsDevice::set_entry_timeout`,
`::set_attr_timeout`, bindings regenerated), and were priced with a throwaway build that took the
values from the environment, over the same three profiles:

| workload | timeout 5 s | entry 60 s | entry 300 s | entry+attr 300 s |
|---|---|---|---|---|
| `/nix`, 1500 reads | 12,515 req (LOOKUP 6,619, GETATTR 333) | 12,515 (5,146 / 1,810) | 11,679 (4,907 / 1,226) | 13,062 (5,568 / 1,929) |
| `/workspace`, 2000 reads | 13,275 (6,912 / 319) | 13,352 (6,771 / 539) | 12,787 (6,261 / 481) | 13,128 (6,521 / 550) |
| 600 execs | 7,303 (4,342 / 318) | 7,451 (4,500 / 311) | 7,378 (4,422 / 310) | not run |

**The entry/attr swap trap, exactly.** A longer entry timeout does drop `LOOKUP` by 20-25% on `/nix`,
but every request it removes comes back as `GETATTR` (333 -> 1,810): `LOOKUP` carries the entry's
attributes, so a dentry that outlives them has to be revalidated separately. Net requests move by
0-5%, and the arm that raises both timeouts is not better than raising one. There is no wall-clock
win here to claim, and the exec profile does not move at all.

The deeper reason the tail is irreducible on these profiles: the remaining `LOOKUP`s name **distinct
paths** - 1500 different store binaries, 2000 different workspace files, each resolved by a fresh
process - so there is no repeat for any timeout to cache. What the knobs would help is a workload
that re-probes the *same* names, and the shipped 250 ms negative entry already covers the miss
half of that.

So: keep the setters (they are per device, off-cang's-default-path, and a content-addressed store
that does repeat names can use them), but they are not the next lever, and they do not on their own
justify the `/nix` export.

## 6. Open, in order

1. A **read-only `/nix` export** as a second `FsDevice` - justified now by *enforcement and
   isolation*, not by timeouts: the store is the one subtree that can be read-only in the guest, its
   own worker pool keeps store lookups off the workspace's queue, and it is the only way to scope
   `xattr = false` (which is the one lever left that removes the per-exec `security.capability`
   probe). The device budget is **19 virtio-mmio IRQs** on x86 (`IRQ_BASE 5` .. `IRQ_MAX 23`,
   `arch/src/x86_64/layout.rs`) against **7 used** in a real boot, so a second export costs one IRQ;
   `NO_OPEN`/`NO_FLUSH`/`CACHE_SYMLINKS`/`negative_entry` are then set per export. DAX stays out:
   note 05 dropped it for the root connection on boot-brick risk, and a `/nix` export carries the
   same boot binaries, so the risk does not shrink just because the export does.
2. `/workspace` on its own export is *not* worth it for policy reasons: the big levers are wanted on
   both shares and `/workspace` is the one that can only be tightened. Its case is ticket 18
   (a block device for `target/`), not tuning.
