timesync: Enable timesync for Linux

VMs on (at least) Linux have clock delayed behind the host clock by as
many as several hundred milliseconds after their start.  This can cause
different problems, one of them being that files accessed via virtiofs
can have future time stamps temporarily, possibly breaking
compilation (see ).

Timesync is currently enabled only on MacOS.  This commit enables it
also on Linux.  This doesn't solve the clock difference problem
completely because it takes some time before the first clock
synchronisation happens.  Enforcing the synchronisation earlier is
addressed in the next commit.

Enabling timesync on Linux should also fix possible troubles with
systematic clock drift issues, see #756.

Fixes #756.

----- 32eb92b5965059b46acd2378f31a36fa09b161e8 Tue Sep 1 17:08:00 2026 +0200
timesync: Allow an explicit time sync request from a guest

When a guest starts, its clock is delayed against the host clock
significantly, up to several hundred milliseconds.  The exact cause is
unknown, kernel kvm clock handling is suspected.  For the lack of a
better fix, some workaround is needed.

One way would be to use /dev/rtc*.  But it has only whole-second
precision.  This means the clock can be synchronised precisely only when
second changes, forcing waiting with the synchronisation up to 1 second.
Moreover, vhost-user-rtc must be used, or built-in virtio-rtc
implemented.

Another possible and simpler workaround is to use the timesync
mechanism.  But there is the problem that the host sends the first
timesync request before the guest is ready to accept it.  Then the sync
must wait for the next timesync cycle, i.e. 60 seconds.

Let's remedy this problem by allowing the guest to send an explicit
request for timesync to the host.  The request is sent from init, when
the guest clock worker is started.  If a VM uses its own init, it must
implement its own timesync mechanism.

The introduced mechanism may possibly fail under some scenarios but it
should work usually and should be in any case improvement over the
current situation.  If a precise time is reliably needed, other
synchronisation means should be used, e.g. chrony.

Fixes #775.

----- 6d800f985322bffa16b1b867c5f889f8e76a469d Sat Sep 5 19:26:49 2026 +0200
timesync: Reduce DELTA_SYNC to 10 ms

DELTA_SYNC value defines how much guest-host clock difference is
tolerated by the guest when obtaining timesync messages.  The current
value feels to be a bit too much, it may be possibly too large for
issues like #775.  Let's reduce it.

A related benefit is that a sufficiently low value enforces time
synchronisation at the VM start, causing the VM to observe a relatively
precise time when its workload typically starts.  For example, the
example chroot VM exposes an initial time difference of about ~70 ms in
my environment, which is below the current limit but well above the new
limit.  While this initial synchronisation could be enforced by other
means, it'd be pointless if we thought 100 ms time difference is OK.

The new value of 10 ms is arbitrary, not a scientific decision.
