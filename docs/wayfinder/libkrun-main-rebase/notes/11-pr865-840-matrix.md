## Verdict

**Both PRs apply to `main`'s post-rewrite tree, cleanly, as ordered sequences.
Neither is partially superseded. Carry 3 commits of 865 and 4 of 840.**

* **865 — apply as-is.** All three commits cherry-pick cleanly in order onto
  `upstream/main` (`a980e779`); the composite 3-way merge of the whole PR into
  `main` is clean (`git merge-tree` exits 0). It postdates the rewrite, so it
  already targets `src/libkrun/src/api/device_builders.rs`, the post-`src/vmm`
  tree, and `src/vmm`-free paths. No fork-side conflict either: the 16 fork
  commits touch none of 865's files except `include/libkrun.h`, and the PR's
  `include/libkrun.h` hunk auto-merges even against a synthetic
  main+fork-`libkrun.h` file (raw evidence:
  `11-raw-pr865-cherrypick-matrix*.txt`, `11-raw-pr865-sequential-onto-main.txt`).
* **840 — apply as-is, then decide about `TIMESYNC=1`.** All four commits
  cherry-pick cleanly in order onto `upstream/main`; composite merge-tree clean.
  The ticket's premise that 840 "predates the 2026-09-11 ABI rewrite" is **stale**:
  the author rebased the branch on 2026-09-14/15, so `a3d31822` is an ancestor of
  `2f37b0a3` and its files (`init/init-binary/src/timesync.rs`,
  `src/devices/src/virtio/vsock/*`, `Makefile`) are all on the post-rewrite tree.
  Nothing in main supersedes it: no other clock fix landed, and the only commits
  after the PR base touching those paths are unrelated init moves and Windows
  fixes. **But** the guest half is compiled out unless the init blob is built with
  `--features timesync` — see §4.
* **The fork-tip (`cang` = `28e79624`) cherry-pick matrix is not the conflict
  surface that matters.** Its conflicts are all "the fork is still the v1.19.5
  tree": `block/device.rs` uses imago's old `SyncFormatAccess` (main has
  `FormatAccess`), and the fork has no `src/libkrun/src/api/device_builders.rs`,
  no `bindings/libkrun-via-cdylib-weak/ffier-krun.json`, no `init/init-binary`.
  After ticket 04's rebase those files come from `main`, so 865/840 see main's
  versions. Only `include/libkrun.h` is shared, and it merges.

## 2. Does the payload still make sense post-rewrite?

**865 — yes, unambiguously.** Its base `e6cdb553` is a descendant of `a3d31822`;
the branch was cut *after* the rewrite. Evidence that it targets the post-rewrite
tree: it edits `src/libkrun/src/api/device_builders.rs` (a file the rewrite
introduced — it does not exist in 1.19.x), and its diff has no `src/vmm` path and
no old-C-API hunks. `main` has no pre-existing parallel-read/thread-pool work in
`src/devices/src/virtio/block/` (`git grep -i 'thread pool|parallel' src/devices/src/virtio/block/` → empty), so
#824 is not fixed upstream in some other way; there is nothing to be superseded.

**840 — yes, but the ticket's premise is wrong about *where*.**
`a3d31822` is an ancestor of `2f37b0a3`, so 840 is *not* a pre-rewrite PR: the
author force-pushed the branch on 2026-09-14/15 (commits dated 09-14/09-15 while
the PR was opened 2026-09-05; the head moved from the ticket's "created
2026-09-05" description). Concretely it touches no code the rewrite moved:

* it does **not** touch `src/vmm` (which the rewrite relocated to
  `src/libkrun/src/vmm`), nor the new `src/polly` / `src/whp` crates, nor
  `include/libkrun.h`, nor the C API;
* its three source paths are `src/devices/src/virtio/vsock/{mod,muxer,timesync}.rs`
  (device code, unchanged by the ABI rewrite), `init/init-binary/src/timesync.rs`
  (post-rewrite guest PID-1 init) and the build `Makefile`.

Is the clock work still needed? Main has no other fix: after the 840 base the only
commits touching those paths are unrelated (`454157ae init: move PID-1 binary and
init-blob crates under init/`, Windows/clippy/build fixes). The problem the PR
addresses (#775, #756: guest clock one to several hundred ms behind the host at
VM start, suspected kvm-clock handling; future mtimes over virtiofs breaking
builds) is orthogonal to the ABI rewrite and unfixed in `main`. The workaround
itself is: (a) enable the already-existing `TimesyncThread` on Linux, (b) let the
guest ask for an immediate sync instead of waiting up to the 60 s
`UPDATE_INTERVAL`, (c) tighten the guest's accepted delta from 100 ms to 10 ms,
(d) actually build the guest init with the feature that enables it.

## 3. Opt-in surface of 865 — and what stays off

**What turns it on: a new per-block-device setter, default `false`. Nothing else.**

* C API (`include/libkrun.h`, on the `KrunBlockDevice` object):
  `void krun_block_device_set_parallel_reads(KrunBlockDevice handle, bool enabled);`
  plus the weak-linking typedef `krun_block_device_set_parallel_reads_fn` and the
  ffier schema entry `set_parallel_reads` / `krun_block_device_set_parallel_reads`.
* Rust API (`src/libkrun/src/api/device_builders.rs`):
  `BlockDevice::set_parallel_reads(&mut self, enabled: bool)`; the field is
  initialised `parallel_reads: false` in `BlockDevice::new` and copied into
  `Block::new(..., parallel_reads)`.
* Plumbing: `Block::new` gains the `parallel_reads` field; `VirtioDevice::activate`
  passes `self.parallel_reads` to `BlockWorker::new`; the worker runs
  `let (read_tx, mut read_workers) = if parallel_reads { … };` — when `false` the
  pool is **not spawned at all** (`(None, Vec::new())`) and reads are processed
  inline on the epoll thread. Even when `true`, writes/flushes/discards stay on
  the device thread; only reads go to a pool sized
  `available_parallelism().clamp(2, 8)`.
* There is **no cargo feature, no env var, no config-file field, no device
  property** for it.

**What stays off in the rebased cang.** This map does not wire new knobs into cang,
and cang never calls `krun_block_device_set_parallel_reads` (its Rust launcher uses
`krun_add_disk`, `crates/cang/src/runtime/vm/libkrun/launcher.rs`), so:

* the thread pool is never created, `ReadJob`/`SharedState`/`read_worker` stay dead
  code for cang, and cang's virtio-blk reads keep their current serialized
  behaviour on the device thread;
* the only live part of 865 in cang is commit `802c9e1e`'s `Mutex<FormatAccess<..>>`
  → `RwLock<FormatAccess<..>>` refactor (plus `file_traits.rs` `read()`/`write()`
  accessors) — a lock-type change with no behaviour toggle. It is safe on its own
  (single reader/writer at a time until the pool is enabled) but it is *not*
  opt-in and ticket 04 should not try to "gate" it.

**840 has no runtime knob either**: it is build-time only (`TIMESYNC=1`), and its
host-side Linux enablement is not behind any cargo feature at all — see §4.

## 4. Prerequisites from the rest of the stack

### 865 — none

No kernel/firmware change, no host tooling, no dependency addition. The only
build-time requirement is that libkrun is built with `BLK=1` (the device is
`#[cfg(feature = "blk")]`) — the fork's `publish-cang-release.yml` already does
`make BLK=1 NET=1 GPU=1 SND=1 INPUT=1`, and cang adds disks through
`krun_add_disk`. `libkrunfw` is untouched.

### 840 — a build-flag prerequisite for the guest half, and a cang-wiring one

1. **Kernel/firmware: none.** The mechanism is AF_VSOCK `SOCK_DGRAM` to port 123
   (`init/init-binary/src/timesync.rs`, `src/devices/src/virtio/vsock/timesync.rs`).
   cang already depends on virtio-vsock for its attach path, and the pinned
   `libkrunfw v5.6.2-cang.1` kernel has vsock enabled. Nothing in `libkrunfw`
   changes.
2. **Host half: compiled unconditionally on Linux after the cherry-pick.** The
   `timesync` cargo feature is an *empty no-op* for the host library
   (`src/devices/Cargo.toml: timesync = []`; there is no
   `#[cfg(feature = "timesync")]` anywhere under `src/devices/` or `src/libkrun/`;
   the only real `feature = "timesync"` gates in the tree are in
   `init/init-binary/src/main.rs` and `init/init-blob/build.rs`). 840's commits
   change the cfg from `#[cfg(target_os = "macos")]` to
   `#[cfg(any(target_os = "macos", target_os = "linux"))]` on the vsock timesync
   module and its muxer call site, so on Linux the VMM starts a `TimesyncThread` as
   soon as the commits land. With no guest listener that is harmless (the guest
   just ignores the datagrams), but it *is* a behaviour change ticket 04 should
   record rather than expect `TIMESYNC=1` to gate.
3. **Guest half: needs the init built with `--features timesync`.** Main's guest
   PID-1 init is `init/init-binary`, embedded into `init/init-blob` by
   `init/init-blob/build.rs`, which forwards the `timesync` feature to the inner
   `cargo build --features timesync` (build.rs:144-158). Before 840, the Makefile
   built the blob with a hard-coded `--features ffi` (`cargo build --release -p
   krun-init-blob --features ffi`), so `make TIMESYNC=1` enabled the host half but
   the embedded init stayed without timesync. **Commit `2f37b0a3` is exactly the
   fix** (`INIT_BLOB_FEATURE_FLAGS = --features ffi`; `+ --features timesync` when
   `TIMESYNC=1`; used at Makefile:237/255). It must be carried together with the
   other three commits or the guest-side workaround cannot run.
4. **cang's own build flag:** the fork's release workflow
   (`.github/workflows/publish-cang-release.yml` on `cang`) invokes
   `make BLK=1 NET=1 GPU=1 SND=1 INPUT=1` — **no `TIMESYNC=1`**. The 1.19.5 fork
   Makefile has no `TIMESYNC` variable at all, and no cang source or nix file
   mentions timesync. So after the rebase **cang must add `TIMESYNC=1` to that
   make line** (a fork-CI change) for 840's guest half to reach a guest; otherwise
   the host half runs but no guest ever binds the timesync socket or asks for a
   sync, and the PR is inert in cang's shipped artifact.
5. **ABI-2 init wiring decides whether the guest half is even in play.** On main
   `libkrun.so` no longer embeds an init blob (no `INIT_BINARY` / `krun-init-blob`
   reference under `src/libkrun/`); the init is the separate `libkrun_init.so`
   built from `init/init-blob`/`init/init-binary`, exposed through the new
   `include/libkrun_init.h` API. 840's guest half lives in that init binary. If
   ticket 09/10 keep cang on libkrun's default init, the `TIMESYNC=1` blob is what
   runs; if cang ships its own init, that init must implement the request itself —
   840's own commit message says so explicitly: *"If a VM uses its own init, it
   must implement its own timesync mechanism."* cang's `cang-guest-init` does not
   today (no timesync anywhere in `crates/`), and cang's exec path is
   `.../bin/cang-guest-init` executed by libkrun's implicit init, so today it is
   libkrun's init that would send the request.

## 6. Conflict surface ticket 04 should expect (and not expect)

* **Expect none for 865/840 themselves**: sequential cherry-picks and the
  composite merge-tree are clean on `upstream/main`, and — after the fork commits
  are rebased — the only shared file is `include/libkrun.h`, whose new
  `krun_block_device_set_parallel_reads` declaration sits in the block-device
  section while the fork's additions (`krun_set_gpu_options3` around v1.19.5:644,
  `krun_set_kernel_cmdline_append` around v1.19.5:1226) sit in other sections; the
  cherry-pick auto-merges it.
* **Do not read the fork-tip matrix as the conflict surface.** `block/device.rs`,
  `block/worker.rs`, the missing `device_builders.rs`/ffier JSON and the missing
  `init/init-binary/src/timesync.rs` are all pre-rewrite shape differences that the
  rebase itself removes. In particular:
  * `src/devices/src/virtio/block/device.rs`: fork uses imago's
    `SyncFormatAccess` under a `Mutex`; main (post PR-822's dependency commits)
    uses `FormatAccess`; the PR moves that to `RwLock` — no manual port needed on
    main.
  * `bindings/libkrun-via-cdylib-weak/ffier-krun.json` and
    `src/libkrun/src/api/device_builders.rs` only exist post-rewrite; the rebased
    tree has main's, which the PR's hunks match exactly.
  * `init/init-binary/src/timesync.rs` only exists post-rewrite (main moved the
    C `src/init_blob/init/init.c` and the Rust init under `init/`); the rebased
    tree has main's version, which the PR's hunks match exactly.
* **The fork rebase itself is where the conflicts are** (ticket 04 step 2, ticket
  10), not in these two PRs.

## 7. What this changes in ticket 04's plan

1. **Ticket 04's step 3 premise about 840 is stale** — 840 (head `2f37b0a3`,
   rebased 2026-09-14/15) already contains the 2026-09-11 ABI rewrite; it touches
   no `src/vmm`/`src/polly`/`src/whp`/C-API code and needs no rewrite adaptation.
   Record it as "post-rewrite despite the 2026-09-05 PR creation date".
2. **865 needs no adaptation either** and applies cleanly as a 3-commit sequence;
   the "conflicts in GPU files / `src/libkrun/src/lib.rs` / builder" predicted in
   step 2 belong to the 16 fork commits, not to 865/840.
3. **Add a fork-CI action item**: `.github/workflows/publish-cang-release.yml`
   must gain `TIMESYNC=1` (alongside `BLK=1 NET=1 GPU=1 SND=1 INPUT=1`; note SND is
   the one main removed — ticket 10's scope) or 840's guest half is compiled out of
   the shipped prebuilt. Decide this explicitly; it is a *fork* artefact, not
   something the rebase gets for free.
4. **State what cang gains**: 865's thread pool is dead code unless a knob is
   wired (out of scope for this map), and the only live 865 change is the
   RwLock refactor; 840's host Linux enablement is live on cherry-pick but inert
   without `TIMESYNC=1` and an init that requests a sync. Ticket 08's GPU smoke and
   the other smokes will not notice either PR.
5. **Ticket 10 note**: the fork's `include/libkrun.h` re-additions do not collide
   with 865's new declaration, so no ordering constraint between tickets 04 and 10
   beyond the usual "rebase first, then re-add the C extensions".
